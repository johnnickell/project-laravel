# Align the Laravel Application Foundation and Shared Authorization

## Destination

Turn the starter from a Fight package-support certification consumer into a Laravel-owned application
foundation with current package contracts, behavior-focused verification, a running-Compose build gate,
and one application authorization boundary for every API operation and future MCP operation.

Preserve Laravel, Eloquent, Pint, the `App\` namespace mapped to `app/`, exact 100% owned-production statement
coverage, and Fight Common/AccessControl ownership of their public Domain and Application behavior.
Align engineering semantics strongly without importing another application's framework, persistence stack,
planning lifecycle, or private implementation.

The human maintainer approved this direction in the adoption discussion and requested this epic.
The epic was approved for requirements TICKET decomposition, not direct implementation as an undecomposed epic.
Delivery is now in progress through the separately approved TASK-00001. The separately approved planning lifecycle uses EPIC → TICKET → TASK, with optional PRDs. No application release version has been selected; `target: TBD` is intentional.

## Decisions so far

### Package baseline and ownership

- Upgrade to a verified, mutually compatible Fight Common 1.2+ and Fight AccessControl 0.4+ release baseline.
  Evaluate AccessControl 0.5 when available; do not assume publication or make waiting for it an implicit blocker.
  The approved [T-00006 baseline](../tickets/00006-TICKET.md#approved-release-baseline) is Common 1.2.0 /
  AccessControl 0.4.0. TASK-00001 installs both releases and records bounded local integration in the
  [installed-contract handoff](../wayfinder/fight-package-baseline.md). Full AccessControl behavior,
  authoritative persistence, and shared permission policy remain separate downstream work.
- The inspected baseline at application commit `e43ed226f811a90f08b6d9312396ff41c7bfc33b` is Common
  `dev-develop@ce212af215d4ddf8d70f349b7a8c5e634dc9e539` with a compatibility-only `1.2.0-dev` alias,
  AccessControl `dev-develop@4259ea0b77bc2e1d87e62ab70b64af63bae99477`, and Laravel `v13.31.0`.
  These installed snapshots do not establish the new release baseline.
- Do not introduce new integration with the retiring `UnitOfWork`, `RoleAdministrationAuthorization`, or
  `AgentPermissionAdministrationAuthorization` contracts. Verify the selected packages' transaction and
  principal/permission APIs rather than adding aliases or scaffolding around outgoing interfaces.
- Continue consuming public package messages, handlers, Views, and capabilities directly. Laravel owns
  composition, transport, Eloquent mappings/repositories, operations, and genuinely application-owned policy.
  Do not copy package source, rename package behavior behind forwarding wrappers, or add a Fight Laravel package.
- Retain inward dependencies: Adapter to Application to Domain. Providers are composition, not a license for
  service location in Domain/Application. Owned orchestration must enforce real application policy or coordinate
  demonstrated ownership boundaries; it must not exist merely to rename a package use case.
- Domain remains focused on cohesive business responsibilities and intrinsic invariants, generally without
  invocation or transport knowledge. Application owns invocation authorization; transport establishes trusted
  context. Preserve intrinsic Domain ownership rules rather than moving all business policy into authorization.

### Shared permission enforcement

- Every API and future MCP operation, including queries, passes through the same application authorization
  boundary before protected use-case execution. No transport receives an implicit permission bypass.
- The invocation supplies trusted actor context, the operation, and its target where applicable. Each operation
  has an explicit access policy; missing mappings or required authority fail closed. Any unauthenticated entry
  operation must be explicitly classified, not accidentally exempted by absent middleware.
- Evaluate permissions and target/ownership constraints against authoritative package-backed state, not role
  names, UI visibility, route reachability, or client/token permission claims alone. Keep package-owned invariants
  in the package and add only application-owned access rules.
- Laravel Gates/Policies provide framework-facing integration with this shared application policy. Route
  middleware, Form Requests, Actions, and MCP handlers must not become independent policy authorities or the
  sole enforcement point. Application code does not depend on Laravel facades or concrete adapters.
- Protected non-HTTP execution must enforce the same application rule. Worker/system authority, where needed,
  is explicit rather than an HTTP-only check being silently skipped. Scope cached principal authority to one
  request or job; do not leak it across long-running workers.
- Keep package commands and queries intact. Invocation context can be supplied separately without teaching
  Domain objects about HTTP or MCP. The selected public package APIs determine the exact integration design.
- HTTP uses thin single-interaction Actions and named Responders, validated transport input, safe package Views,
  and explicit representation mapping. Responders own status, headers, API JSend presentation, and safe boundary
  mapping, not data fetching or permission policy. Do not turn the existing HTML homepage into a JSON API.

### Application verification, not package certification

- Retire the starter's package-support certification obligation: support receipts, receipt/hash validators,
  lowest/latest certification locks and lanes, complete-provider resolution inventories, and tests whose only
  purpose is certifying upstream package behavior. Do not relocate this machinery into another application gate.
- Retain or replace tests only where they demonstrate an actual owned application contract or important
  application integration: observable outcomes, rejection/failure behavior, state changes, and external effects.
  The same package feature may remain covered when an owned use case genuinely depends on it.
- Remove product-suite architecture, configuration, wrapper, generated-artifact, tooling, and test-infrastructure
  meta-tests. Validate those concerns through their owning tools and direct inspection, without deliberately
  invalid fixtures created just to test a quality tool.
- Preserve exact 100% owned-production statement coverage and honest source-denominator reporting. Do not lower
  the threshold, exclude meaningful owned behavior, or manufacture wiring assertions to obtain the percentage.
  Report unit evidence separately from combined integration/functional coverage; a percentage does not prove
  authorization or protocol correctness.
- Preserve the existing homepage smoke behavior. Add tests at the narrowest real boundary that proves a claim;
  functional HTTP claims require an actual interaction, not a test-only production route or mapper-only evidence.

### Running-Compose canonical gate

The direction below was approved before develop PR #9 added a distinct lean-gate requirement. Its full scope is
now [T-00011](../tickets/00011-TICKET.md); T-00007 and T-00011 are `needs-info` until their Unit-only/all-suite
coverage, PHPCS, production-install and CI lifecycle requirements are reconciled. This migration preserves both
and does not silently override the earlier decisions or authorize a gate implementation.

- `./bin/build` becomes a thin Docker Compose exec wrapper that invokes `scripts/build.php` inside the already
  running application stack. It fails clearly if the required service is unavailable; it does not build images,
  install/update dependencies, or silently bring up the stack.
- The PHP orchestrator runs named, fail-fast phases: PHP syntax checks, Pint, compatible PHPCS rules, PHPStan,
  Deptrac, Rector dry-run, and one coherent Pest/coverage execution of all configured application suites.
  Coverage enforcement consumes that execution rather than rerunning the same suites.
- Keep Pint as the formatter. Adapt additional PHP/naming/documentation rules so the checks agree rather than
  blindly installing a competing formatting policy. Prefer explicit injection, strict types, intent-named
  messages/handlers, and immutable values, with justified Laravel model/framework exceptions.
- Run frontend compilation and checks appropriate to actual owned frontend behavior. Future lint, type,
  component, and browser checks are added with their real boundaries, not with speculative harnesses.
- Image creation, dependency installation/updates/audits, and runtime lifecycle remain explicit operations through
  repository-owned setup and lifecycle commands. Developer-tool and Laravel cache artifacts stay in `var/cache/`.
- CI prepares dependencies and starts the stack explicitly, invokes the same `./bin/build`, and cleans up its
  resources. Preserve fail-fast hosted verification and distinguish local results from exact-head hosted results.
  Retain repository planning validation without introducing new Python build orchestration or duplicating it.

### Persistence and delivery guarantees

- Keep Laravel/Eloquent and the local MySQL direction; do not import Slim, Doctrine, or PostgreSQL assumptions.
  Persistence adapters reconstruct package aggregates without making Eloquent records the Domain model.
- Use the selected package transaction contract on the same connection as participating repositories. The owning
  use case controls atomic state, required audit evidence, and required durable delivery intent.
- External effects occur after commit. After-commit queue dispatch alone does not establish crash-safe delivery;
  required effects need recoverable durable intent and explicit retry/idempotency guarantees. Do not claim
  exactly-once external delivery. Reuse package guarantees rather than implementing competing mechanisms.

## Completion criteria

- A selected installable package baseline is locked and exercised through real Laravel application contracts,
  without outgoing-interface compatibility scaffolding or a recreated support-certification subsystem.
- The certification artifacts, lanes, and certification-only/meta-tests are retired; meaningful application
  behavior remains covered with exact owned-production coverage and an explicit denominator.
- Local and hosted verification use the thin running-stack wrapper and PHP orchestrator, with one application
  suite/coverage execution, explicit setup prerequisites, and clear failure behavior.
- All API operations introduced or retained in scope have explicit access classification and cannot bypass the
  shared application authorization boundary. Real HTTP and non-HTTP application tests demonstrate permitted,
  denied, missing-policy, stale/revoked-authority, and target-ownership outcomes where applicable.
- The same application contract is usable by a future MCP adapter without a second permission implementation;
  no MCP transport or synthetic endpoint is required to prove this epic.
- Representative package use cases prove Eloquent/transaction compatibility, rollback, and any claimed
  audit/durable-effect guarantees. Only demonstrated application needs introduce new production abstractions.
- Local instructions, current context, setup documentation, CI guidance, and affected planning projections
  describe the new contract without claiming full API/SPA delivery or erasing historical certification results.

## Out of scope

- Implementing the complete AccessControl API/SPA capability map, an MCP server or tool catalog, or production
  deployment. Shared authorization is required for future MCP, but MCP transport implementation remains deferred.
- Publishing or modifying upstream packages, copying their Domain/Application source, selecting speculative
  breaking migrations, or waiting indefinitely for an unreleased AccessControl version.
- Replacing Laravel, Eloquent, Pint, or `app/`; adopting another framework's database/runtime assumptions.
- Package releases, tags, Packagist publication, template enablement, archives, or a global standards rollout.
