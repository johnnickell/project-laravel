# Adopt Prospective Acceptance and Closeout Rules

## Outcome

Deliver one discoverable prospective acceptance/administrative-closeout contract in
`planning/CONVENTIONS.md`, referenced from relevant local entrypoints and the TASK template. Future TASKs
explicitly adopt the contract without reinterpreting existing acceptance. This single TASK covers all accepted
criteria of [TICKET-00014](../tickets/00014-TICKET.md); it does not introduce a new reporting or automation subsystem.

## Scope

- In scope: the authoritative local policy, relevant AGENTS/contribution/planning entrypoint references and
  explicit-adoption support in the TASK template; candidate A/B classification, proof and continuation rules;
  current handoff/eligible-parent synchronization; evidence ownership; direct independent scenario walkthroughs.
- Reference provider-owned Review/QA/Land contracts and accepted local report conventions rather than copying
  shared skills. Reconcile conflicting current instructions within this scope while preserving historical
  TASK contracts, findings, immutable evidence and the existing human merge boundary.
- Out of scope: provider/harness changes, global installation/enrollment, CI/gate redesign, new report
  generators/validators, product behavior or product-suite meta-tests, actual archives/releases/deployments,
  historical acceptance amendments, and rebuilding TASK-00008's delivered routing/delivery safeguards.
  Naming migration and workflow/report binding remain TASK-00009/TASK-00010 scope.

## Validation and permissions

No new business actor, target permission, product payload, domain event or external runtime effect is introduced.
Publication, evidence collection, implementation repair and human merge retain their distinct authorities.
A policy or template reference is not permission to execute or publish a workflow. Sanitize public evidence and
retain ignored reports outside disposable worktrees; Land and builders must not rewrite independent verdicts.

Require explicit repository/TASK/requirements/candidate identity and any applicable provenance bridge. A green
local build, old report, `done`, OPEN PR or equal tree alone does not establish complete acceptance or delivery.
Missing authority or contradictory literal-final-head acceptance criteria require a named owner decision, not
silent weakening, status-commit loops or an assumed administrative exception. Executable instruction/policy
changes in this TASK are substantive implementation, not administrative closeout.

## Acceptance criteria

- [ ] `planning/CONVENTIONS.md` owns the accepted prospective contract. Relevant entrypoints and the TASK
      template reference it and support explicit adoption for future TASKs, without automatic retrospective
      application or competing copies of shared workflow/report rules.
- [ ] Accepted A requires the local gate, independent technical acceptance, applicable QA satisfied or justified
      overall N/A, and required hosted/public-contract acceptance proof. Permitted B contains only truthful
      completion/review/PR metadata, factual current-handoff updates and regenerated views. Requirements,
      executable instructions, code, dependencies and behavior changes require reassessment rather than
      inheriting A's acceptance; unknown scope or uncertain integration stops for reconciliation.
- [ ] Fresh required B proof gates successful landing and owned-resource cleanup: exact source-head testing,
      or a verified PR merge candidate with the same complete Git tree and recorded repository/run/event,
      head/base/tested-commit provenance, required jobs and warnings. Stricter explicit source-head requirements
      prevail. A's run, stale/wrong-subject evidence or skipped required jobs cannot stand in for B's proof.
- [ ] Canonical independent reports/findings remain intact. Land verifies permitted A-to-B scope and any
      mechanical bridge, records delivery results in ignored evidence and the PR body, and does not request
      another independent verdict solely for permitted metadata, changed IDs or newly available delivery CI.
- [ ] Closeout synchronizes eligible parents, authored current handoffs and generated views in one operation,
      preserving dependency edges, live delivery checks and historical checkpoints. Missing/infrastructure-failed
      proof retains draft/resources without status toggling; demonstrated implementation defects require repair,
      fresh review and affected QA. After verified B, no tracked "CI passed" commit is needed. Human merge is separate.
- [ ] Independent non-UI QA walks permitted closeout, substantive instruction/code changes, stale/missing proof,
      identical-tree provenance versus stricter source-head criteria, contradictory subjects/requirements and
      missing authority. It distinguishes infrastructure failure from actual defects and confirms the finite
      continuation without mutating independent reports or publishing/dispatching unauthorized work.
- [ ] Planning refresh/checks, live delivery checks, diff checks and the canonical local build pass; independent
      Review, applicable QA and required hosted proof are recorded for this TASK. Current parent/Board/Roadmap/
      context handoffs describe the actual scoped delivery without claiming TICKET-00013 or the broader map complete.
